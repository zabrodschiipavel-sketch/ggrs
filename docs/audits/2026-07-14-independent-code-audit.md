# Независимый аудит ggrs

Дата: 2026-07-14
Объект: весь workspace `ggrs` (`ggrs-core`, `ggrs-model`, CI и публичные форматы файлов).
Режим: статический анализ публичного API и unsafe-кода, запуск тестов и линтеров. Изменения кода в рамках аудита не вносились.

## Итог

Обычные покрытые сценарии работают, однако библиотека не готова к безопасному использованию с конкурентным доступом или недоверенными входными данными. До устранения находок P0 нельзя заявлять memory safety и потокобезопасность публичного API.

## Находки

### P0 — `Context` небезопасно доступен из нескольких вычислений

`Arena` объявлен `Sync` вручную, а `compute` принимает `&Context` и изменяет арену через сырые указатели. Поэтому корректный с точки зрения типов Rust код может одновременно вызвать `compute` дважды для одного `Context`. Оба вызова записывают одни и те же выходные тензоры; это data race и undefined behavior.

Ссылки: `crates/ggrs-core/src/context.rs:15`, `crates/ggrs-core/src/compute.rs:10-43`.

Рекомендация: запретить одновременное выполнение на одном контексте на уровне типов или синхронизации. Например, дать исполнению эксклюзивный lease от `&mut Context` и ограничить внутреннее unsafe-расшаривание областью одного вызова; не оставлять `Context` глобально `Sync` без механизма сериализации.

### P0 — публичный `get_f32` читает память без проверки границ

`Context::get_f32` проверяет только dtype, затем вычисляет адрес и разыменовывает его. Он не проверяет, что каждая компонента `idx` меньше соответствующей `ne`. Вызов с индексом вне тензора может прочитать соседнюю память арены либо выйти за её пределы, что является UB.

Ссылка: `crates/ggrs-core/src/context.rs:168-172`.

Рекомендация: до вычисления адреса проверять все четыре размерности, а вычисление смещения выполнять через `checked_mul` и `checked_add`.

### P0 — переполнение размерностей создаёт некорректные тензоры в release-сборке

`new_tensor`, `row_size`, `nelements`, `nrows` и вычисление страйдов используют обычные умножения `usize`. В debug-сборке это обычно паникует, но в release переполняется с обходом. Например, размер первой оси F32 может переполнить размер строки до нуля; после этого код создаёт слишком маленькую арену и формирует из неё огромный slice либо пишет за границы.

Ссылки: `crates/ggrs-core/src/context.rs:41-46`, `crates/ggrs-core/src/dtype.rs:155-159`, `crates/ggrs-core/src/tensor.rs:23-31`.

Рекомендация: централизовать проверяемый расчёт layout тензора и возвращать ошибку или контролируемую панику до любой аллокации. Проверить тем же путём выравнивание `arena_used + 31`.

### P1 — forward поддерживает broadcast, autograd — нет

`binary_op` допускает broadcast второго операнда. В `build_backward` ветка `Add` требует полного совпадения форм; для `Mul` не выполняется суммирование градиента по broadcast-осям. В результате корректный forward-граф с broadcast не строит backward или даёт градиент неверной формы.

Ссылки: `crates/ggrs-core/src/context.rs:550-563`, `crates/ggrs-core/src/backward.rs:53-77`.

Это известно в текущем self-audit как ограничение следующей фазы, но противоречит заявлению README о «full autograd» и gradcheck для каждой операции.

Рекомендация: добавить reduce-sum к исходной форме для каждой broadcast-оси и finite-difference gradcheck для Add/Mul с broadcast.

### P1 — паника worker-потока приводит к зависанию `compute`

После каждого узла все worker-потоки ожидают `Barrier`. Если один поток паникует до барьера, остальные ждут его бесконечно, а `thread::scope` ожидает их завершения. Пример триггера: невалидный ID в `get_rows` проверяется уже внутри worker-потока.

Ссылки: `crates/ggrs-core/src/compute.rs:32-43`, `crates/ggrs-core/src/kernels/copy.rs:17-23`.

Рекомендация: валидировать весь граф и данные до запуска workers; ошибки передавать без panic либо добавить отмену/пробуждение всех участников при ошибке.

### P2 — загрузчики недоверенных файлов допускают panic, переполнение и DoS

`TokenBin::load` приводит `u64` к `usize` и умножает длину на два без проверки. Checkpoint reader выделяет память по длинам из файла и умножает их на четыре без лимитов. `Bpe::load` проверяет число merge-пар, но не проверяет, что их идентификаторы уже существуют; повреждённый BPE может дойти до индексирования `decode_table` и завершиться panic вместо `io::Error`.

Ссылки: `crates/ggrs-model/src/dataset.rs:31-50`, `crates/ggrs-model/src/checkpoint.rs:83-97`, `crates/ggrs-model/src/bpe.rs:283-291`.

Рекомендация: конвертировать длины через `try_from`, применять `checked_mul`, сверять с размером файла и вводить лимиты. Для BPE на шаге `i` оба ID должны быть меньше `256 + i`; у GGTK также нужно проверить `vocab_size` и каждый токен.

### P2 — checkpoint-загрузка не атомарна в памяти

`load_checkpoint` записывает очередной тензор в `Context` немедленно после чтения. Если следующий тензор, optimizer state или конец файла окажутся повреждёнными, функция вернёт `Err`, а модель уже будет частично перезаписана.

Ссылка: `crates/ggrs-model/src/checkpoint.rs:169-210`.

Рекомендация: сначала прочитать и проверить всё содержимое во временные буферы, затем одним этапом перенести данные в `Context`.

### P2 — F32 → F16 не соблюдает заявленное округление на краю subnormal-диапазона

При `shift >= 24` конвертер безусловно возвращает ноль. Значения строго выше `2^-25` должны округляться к минимальному F16 subnormal (`0x0001`), например `3 * 2^-26`; текущая ветка обнуляет их. Это противоречит заявленному round-to-nearest-even.

Ссылки: `crates/ggrs-core/src/dtype.rs:8`, `crates/ggrs-core/src/dtype.rs:63-67`.

Рекомендация: обработать guard/sticky-биты и для `shift == 24`, добавить тесты для точной середины, значений чуть ниже и чуть выше неё.

### P3 — CI не проверяет `ggrs-model`

GitHub Actions запускает `cargo test` и Clippy только для `ggrs-core`. Изменения в BPE, checkpoint и dataset не получают CI-проверки.

Ссылка: `.github/workflows/ci.yml:19-21`.

Рекомендация: использовать `cargo test --workspace` и `cargo clippy --workspace --all-targets -- -D warnings`; добавить отдельную release-проверку для сценариев с unsafe-кодом.

## Выполненные проверки

- `cargo test --workspace` — успешно;
- `cargo test --workspace --release` — успешно;
- `cargo clippy --workspace --all-targets -- -D warnings` — успешно;
- `cargo fmt --all -- --check` — код требует форматирования в существующих файлах.

Зелёные тесты подтверждают покрытые нормальные сценарии, но не проверяют перечисленные контракты unsafe-кода, гонки, release-переполнения, broadcast-backward и повреждённые входные файлы.

## Приоритет исправлений

1. Устранить P0 в API и арифметике layout.
2. Убрать зависание на ошибках в многопоточном исполнителе.
3. Реализовать и проверить broadcast-backward либо запретить broadcast до его готовности.
4. Сделать все файловые форматы валидируемыми и checkpoint-загрузку транзакционной.
