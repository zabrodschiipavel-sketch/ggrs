## Найденный и исправленный баг: tok_per_s

Первый калибровочный прогон (d10m, 1000 шагов, до фикса) напечатал финальный `tok/s ≈ 194130`
— подозрительно высоко и подозрительно РАСТУЩЕЕ от шага к шагу (235 → 9609 → ... → 194130).
Перепроверка (правило проекта: числам не верить) по mtime файлов чекпоинта показала реальные
**~89 минут** на 1000 шагов, а не секунды, которые следуют из напечатанного tok/s.

**Корень** (`crates/ggrs-model/src/trainer.rs`, было): таймер `step_start` сбрасывался КАЖДУЮ
итерацию цикла, но делился на него **кумулятивный** `tokens_seen` (накопленный с начала
прогона) — числитель кумулятивный, знаменатель нет, отсюда линейный рост с номером шага.
Затрагивало только информационное поле (CSV/консоль); ни `final_train_loss`, ни веса, ни
resume-побитовость не зависели от него — ни один тест не проверял `tok_per_s` численно.

**Исправлено** в `8bd9d98`: таймер теперь считается от `run_start` (начало цикла обучения
этого вызова `train()`), числитель и знаменатель в одном окне усреднения. Заодно исправлен
задним числом отчёт `docs/runs/2026-07-17-shakespeare.md` (был неверный «813 341 ток/с»,
стало честных ≈412 ток/с по времени `cargo test`, коммит `5dbe4f1`).

loss не тюнился; санity: старт loss 8.3196 = точное совпадение с `ln(4096)=8.317`

**Принятое число для расчёта бюджета: 192 ток/с.**

## Бюджет шагов на 48 часов (формулы из задачного файла)

```
steps_48h  = tok_s × 172800 / 1024 × 0.9   (172800с=48ч; 1024=grad_accum4×t256; 0.9=запас)
           = 192 × 172800 / 1024 × 0.9 = 29 160 шагов  (⇒ ~43.2ч факт. бюджет с запасом)

ckpt_every = tok_s × 1800 / 1024            (≤30 мин потери прогресса при обрыве)
           = 192 × 1800 / 1024 ≈ 337.5 → предлагаю округлить до 300 (≈26.7 мин, чуть чаще
             ради запаса; чекпоинт — дешёвая операция на фоне многочасового прогона)
eval_every = ckpt_every = 300
```

При 29 160 шагах корпус будет пройден на 29160×1024 / 494967388 ≈ **6.0%** (одно случайное
прохождение окон, не полная эпоха) — это нормально для этого масштаба/бюджета, не баг.
